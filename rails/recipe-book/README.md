# Recipe Book

A **Kitchen + Bar** recipe library, built as a rail module on the platform shell.

- **~900 recipe cards** across 25 categories, parsed from markdown into SQLite
  (the markdown corpus is the source of truth; re-import is incremental by content hash).
- **Kitchen:** browse / search / filter, meal planner (slots incl. drinks),
  one aggregated pantry-aware shopping list, and pantry "what can I make."
- **Bar (first-class):** cocktails browsable by base spirit & technique, a saved
  **bar inventory**, and a "what can I pour right now" match.
- **Per-recipe icon:** a small clipart glyph generated by the platform's local
  SDXL model, cached per card, shown beside the title.
- **AI (buffered, via the platform broker):** substitutions, scaling, menu &
  cocktail-pairing building, "turn my plan into a grocery run," grounded Q&A +
  semantic search. No direct Ollama, no token streaming (hosted-buffered).

## Architecture

FastAPI `create_api()` factory (port **8830**), one-connection-per-request SQLite
(WAL), a thin buffered **broker** facade, and a Vite **module-federation remote**
frontend (`base:/recipe-book/`, exposes `./module`, no own chrome — adopts the
shell theme). All routes under `/api/*`; the gateway proxies `/recipe-book/api/*`.

Design: editorial / cookbook aesthetic (serif typography, magazine layout) with
app-grade affordances (checkbox ingredients, inventory ring, action buttons). Color
is fully **palette-aware** — surfaces, text, accent, and the action gradients all
derive from the shell's design tokens, so the module recolors with whatever platform
palette is chosen (see `platform/web/THEMING.md`); only the serif type + layout are
the module's own.

See `docs/PLATFORM_CONVERSION.md` for the build ledger and `docs/design/` for the
approved mockups.

## Seed corpus (first-run hydration)

The recipe corpus (`<Category>/<Title>.md` cards) is the source of truth, but the working
store lives in a mounted named volume, not the image. The committed **`seed/recipes/`** tree is
the initial corpus: it's baked into the image (`COPY seed`) and, on a **fresh/empty volume**, the
app copies it into place and ingests it on first startup (`recipe_book.seed.hydrate_if_empty`, wired
in `create_api`). So a clean `git clone` + `docker compose up` comes up populated — no manual seed
step. A **populated** volume (a real install with the owner's edits) is never touched.

Only the markdown is seeded; the SQLite DB rebuilds from it and the per-recipe icons regenerate
on demand, so neither is committed. After you've added/edited recipes in a live install and want the
committed seed to match again, snapshot the live corpus back into the repo and commit it:

```bash
deploy/refresh-seed.sh                 # -> seed/recipes/ (defaults to container platform-recipe-book-1)
```

## Run (standalone dev)

```powershell
uvicorn --factory recipe_book.api:create_api --port 8830
```

In the platform stack it's built + served for you by `platform/deploy/docker-compose.yml`.
